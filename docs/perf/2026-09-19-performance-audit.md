# WorkIsland 性能报告（团队易读版）

更新日期：2026-09-22

## 2026-09-22 复测：1.1 GB 并不是误报

之前仅凭 `ps RSS` 和一次约 500 MB 的短时样本判断“已经正常”，结论不完整。瘦身预览版连续运行约 37 小时后，用 macOS `footprint` 复测到：

- WorkIsland 进程组合计约 1.29 GB；
- 主进程约 891–914 MB，历史峰值约 3.998 GB；
- 当时 4 个外部 MCP 进程合计约 52 MB，不是这次 1.1 GB 的主因；
- `ps RSS` 只显示约 248 MB，因为它没有完整体现已压缩和换出的内存。

日志找到了直接原因：同一份 97,217,067 字节（约 93 MB）的 Codex 会话文件，在一秒内被触发 85 次 token 采集。旧代码要等一次采集结束后才记录去重时间，因此 85 次请求会同时读取同一文件，造成主进程数 GB 峰值，之后再慢慢回落。这就解释了为什么活动监视器有时显示 1.1 GB，有时又只有 500 MB。

### 本次修复

- 同一个会话正在采集时，后续重复请求直接共用第一次结果，不再重复打开文件；
- transcript watcher 的新增内容改为每块最多 256 KB，正确保留跨块中文和未写完的 JSONL 半行；
- 没有删除历史会话搜索、token 统计、MCP、终端、媒体或任何设置能力。

真实打包代码在 Electron Node 模式下读取同一份 93 MB 文件的压力测试：

| 项目 | 修复后 |
| --- | ---: |
| 同一会话同时触发 | 100 次 |
| 实际打开 transcript | 1 次 |
| 完成耗时 | 248 ms |
| 打包 Electron 采集进程 `phys_footprint` 峰值 | 269,485,592 B（约 257 MiB） |
| 采集并回收后 `phys_footprint` | 144,049,664 B（约 137 MiB） |

真实打包版从本分支启动并完成搜索、设置、MCP 和媒体检查后：

- 主进程当前 `phys_footprint` 约 176 MB，启动与交互历史峰值约 401 MB；
- WorkIsland 桌面核心进程合计约 419 MiB；
- 再计入灵动岛关联启动的一个 Codex 子进程后约 451 MiB；
- 场景包含媒体播放和曾打开的设置 Renderer，不是纯闲置数据。

验证结果：650 项全量测试通过；Developer ID 签名和 DMG 校验通过；搜索输入及清空后灵动岛仍存在；设置与 MCP 页面可用；打包版 CLI 正常；MCP 仍完整列出 13 个工具。

结论：这次修复消除的是已确认的“同一大文件几十次并发读取”异常峰值。它不会让 Electron 达到 Atoll 的原生基础内存，也不能用一次短测证明连续运行数天绝不再增长；但在相同 93 MB 文件和更高的 100 次并发压力下，已经没有复现 1.1–4 GB 的内存风暴。

## 2026-09-20 第二阶段：MCP 生命周期验证

- 使用真实 MCP SDK 连续完成 50 次初始化、列出全部 13 个 WorkIsland 工具并断开连接。
- 50 个测试子进程全部在 2.5 秒限制内退出，没有发现无主 MCP 进程。
- 测试期间工具名称、输入校验、读取功能和设置转发功能保持不变。
- 本机观察到的 3 个现有 MCP 进程均为仍在连接的 Codex 客户端，`ps RSS` 合计约 88 MB、CPU 均为 0%；它们不是上述测试遗留。

结论：当前没有证据支持通过强制超时、共享权限上下文或重写 MCP 协议来减少进程。保守方案只增加生命周期回归测试，不修改 MCP 产品代码，避免影响智能体配置 WorkIsland 的能力。

## 2026-09-20 第二阶段：后台与安装包瘦身

这一步仍然没有删功能，主要收掉两类确定的负担：灵动岛收起时过于频繁的性能采样，以及 Electron 自带但产品用不到的语言资源。

### 后台性能采样

- 性能详情没有打开时，系统 CPU、内存和进程采样从每 2 秒一次改为每 10 秒一次，定时采样次数减少 80%。
- 用户打开性能详情时，会立即刷新一次，并继续保持每 2 秒更新，因此面板体验不变。
- 切换状态始终只保留一个定时器，停止服务后定时器会被清理。
- 相关自动化测试 14 项全部通过。

当前瘦身预览包在“音乐播放、灵动岛可见、曾打开设置窗口”的较重场景下，限定应用进程树实测 30 秒：CPU 中位数 8.3%、P95 17.66%、峰值 31.1%；内存 `top` 中位数 512 MB、`ps RSS` 采样 464 MB。这个场景包含 2 个渲染进程、媒体适配器，以及由岛内会话带起的 Codex 子进程，不能当成纯闲置数据；它说明 500 MB 左右的活动监视器读数在功能展开时可能是正常的，不等于再次出现了 1–2 GB 的会话解析峰值。

## 一句话结论

**WorkIsland 仍比原生竞品重。此前流式读取解决了普通启动并发，但长期运行后仍发现同一 93 MB 文件被 85 次同时采集；本次已把同会话重复采集合并为一次，并限制增量读取块大小。真实 100 次压力测试只打开文件一次，未再出现 1.1–4 GB 峰值；较重功能场景当前约 451 MiB，其中桌面核心约 419 MiB。**

这不是用户看错了，也不只是活动监视器显示方式的问题。

## 优化前和 Atoll 相比有多大差距？

以下数据来自同一台 M4、16 GB Mac，是第一阶段修复前的基线。两个应用都在启动约 20 秒后读取数据；不能用这张旧表代表当前瘦身分支。

| 项目 | Atoll 2.3.3 | WorkIsland 1.5.1 预览版 |
| --- | ---: | ---: |
| 安装后大小 | 42.4 MiB | 313.6 MiB |
| 启动约 20 秒时的主程序内存 | 71 MB | 1,513 MB |
| 本次启动的最高内存 | 128 MB | 1,932 MB |
| 启动后的相关进程 | 3 个 | 5 个桌面进程，另有约 30 个 MCP 进程 |
| 采样末尾 CPU | 0.8% | 18.7% |

直观理解：

- WorkIsland 的安装体积约为 Atoll 的 **7.4 倍**。
- 本次启动约 20 秒时，WorkIsland 主程序内存约为 Atoll 的 **21 倍**。
- WorkIsland 本次启动峰值约为 Atoll 的 **15 倍**。

两款产品功能并不完全相同，所以不能只凭这张表判断产品好坏；但对于同类常驻灵动岛工具，这个差距已经足以说明 WorkIsland 的启动方式需要优化。

## 原始版本为什么会占这么多内存？

### 原因一：启动时把大型 AI 会话文件整本搬进内存

WorkIsland 启动后，会读取最近的 Codex 会话文件，用来补充 token 使用数据。

当前做法类似于：

> 为了找一本书最后几页的统计数字，先把整本书复制到桌面，再把每一行分别剪开。

本机有一份会话文件约 150 MB。当前代码读取它时：

- 刚读完文件，内存约 222 MB；
- 把内容按行拆开后，内存升到约 503 MB；
- 即使处理结束，内存也不会马上全部归还。

更严重的是，启动时可能同时处理 6 份文件。多份大文件一起进入内存，就会把主程序推到 1 GB 以上。本次重启实测最高达到 1,932 MB。

这也是为什么有时看到 1.2 GB，有时又只有 500 MB：处理完成后系统会慢慢回收一部分，但回收时间和最终结果并不稳定。

### 原因二：Codex 自动启动了很多 WorkIsland MCP 后台进程

用户没有手动打开 MCP，不代表 MCP 没有运行。Codex 会按照配置自动启动 WorkIsland MCP。

本机测试时同时存在约 30 个 MCP 后台进程。这些进程几乎不使用 CPU，但每个都会占一部分内存，合计还会额外占用数百 MB。

可以把它理解为：

> 原本只需要一个前台接待员，现在每来一个连接就重新开一间办公室、再安排一个接待员，而且旧办公室没有及时关闭。

现在还不能断言这些进程全部都是“泄漏”，因为其中可能包含多个 Codex 任务的正常连接；但数量没有得到有效控制，内存会随着连接数量增加，这是已经确认的问题。

### 原因三：Electron 让基础体积更大，但不是 2 GB 内存的理由

WorkIsland 使用 Electron，应用内自带一套浏览器运行环境，所以安装后约 314 MiB；其中 Electron 本身约 273 MiB。

Atoll 没有携带 Electron/CEF，安装后只有约 42 MiB。因此，WorkIsland 在安装体积和基础内存上天然会更大。

但 Electron 只能解释“为什么基础成本比原生应用高”，**不能解释为什么启动时会达到 1–2 GB**。启动读取大文件和 MCP 多进程才是目前最需要解决的部分。

### 原因四：后台检查过于频繁

WorkIsland 还会定期检查系统内存、进程、AI 会话文件和额度信息。多个定时任务叠加，会让应用在用户没有操作时仍然持续工作。

这不是本次内存暴涨的最大原因，但会增加闲置 CPU 和耗电，应在前两个问题之后处理。

## 应该怎么优化？

### 第一优先级：不要再一次读完整个会话文件

改成从文件末尾逐块读取，只寻找真正需要的 token 数据；同时：

- 启动时最多处理 1–2 个文件，不再 6 个一起处理；
- 记录上次已经读到的位置，下次只读新增内容；
- 超大文件也要限制单次使用的内存。

预期效果：这是降低 1–2 GB 启动峰值最直接的措施。建议目标是处理 200 MB 会话文件时，WorkIsland 主程序峰值不超过 450 MB。

### 第二优先级：减少 MCP 进程数量

理想方案是让同一个 Codex 只保留一个 WorkIsland MCP 服务，多个任务共享它；至少也要做到：

- 连接关闭后，后台进程及时退出；
- 设置空闲退出时间；
- 限制同时存在的进程数量；
- 使用更轻量的连接程序，不再为每个连接加载完整运行环境。

预期效果：在当前约 30 个实例的环境下，可以减少数百 MB 后台内存。

### 第三优先级：降低闲置检查频率

当灵动岛没有展开、也没有活跃 AI 任务时：

- 不要每 2 秒检查一次；
- 延长到 10–30 秒，或者等系统事件发生后再处理；
- 把多个重复检查合并成一个。

目标：闲置 CPU 中位数低于 1%。

### 第四优先级：缩小安装包

清理发布包里的调试文件、源码映射、类型文件、非 macOS 文件和重复资源。

这可以让下载和安装更轻，但不会直接解决 1–2 GB 运行内存，所以优先级低于前面三项。

## 建议开发顺序

1. 先改会话文件读取方式，并限制启动并发。
2. 再解决 MCP 多进程和退出机制。
3. 用同一批大文件重新测试优化前后差异。
4. 再降低后台检查频率。
5. 最后清理安装包。

不要一开始就重写成苹果原生应用。当前最严重的问题来自具体实现，即使继续使用 Electron，也能先消掉大部分异常内存。等这些问题解决后，再评估是否值得承担原生重写的成本。

## 修复完成的判断标准

开发完成后，至少要达到：

- 启动 60 秒后，桌面应用全部进程合计不超过 400 MB；
- 处理 200 MB 会话文件时，主程序峰值不超过 450 MB；
- 连续连接和关闭 50 次 MCP 后，只剩 0–1 个服务进程；
- 闲置 CPU 中位数低于 1%；
- 测试脚本能分别显示“桌面应用”“MCP”“两者合计”，不再把它们混成一个数字。

## 这份报告还没有证明什么？

- 还没有证明内存会无限上涨；目前看到的是很高的启动峰值和不稳定回落。
- 还没有证明 30 个 MCP 全部是无用进程，需要继续验证它们分别属于哪些 Codex 任务。
- 当前 WorkIsland 是本地主分支预览包，不是重新下载的官方安装包；不过上述两段问题代码在正式版 1.5.1 中也已经存在。
- Atoll 对比是一次同机测试，不是完整市场评测。正式基准还需要重复测试冷启动、暖启动以及运行 15、30、60 分钟后的状态。

## 给开发群的简短版本

> WorkIsland 当前内存偏高已经实测确认。同机启动约 20 秒时，Atoll 主程序约 71 MB、峰值 128 MB；WorkIsland 主程序约 1.51 GB、峰值 1.93 GB，而且这还没有计算约 30 个 MCP 后台进程。主要原因不是单纯用了 Electron，而是启动时并发整读多份大型 AI 会话文件，以及 MCP 每个连接都会拉起独立进程。建议先把会话解析改成增量/流式读取并限制并发，再处理 MCP 复用和退出机制。完成后目标是桌面端 60 秒稳态不超过 400 MB、处理 200 MB 会话文件时峰值不超过 450 MB。
