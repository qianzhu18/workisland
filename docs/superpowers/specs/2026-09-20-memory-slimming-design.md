# WorkIsland 第一阶段内存瘦身设计

日期：2026-09-20
关联 Issue：[#185](https://github.com/qianzhu18/workisland/issues/185)

## 目标

在不删除产品功能、不改变 token 统计结果的前提下，降低 WorkIsland 启动时的主进程内存峰值。

本阶段处理已经复现并确认的三个直接原因：

1. Codex、Claude 会话文件被一次性完整读入并按行复制。
2. 启动回填会同时解析多份会话文件。
3. 历史会话搜索在启动时再次整读所有有变化的 Codex、Claude、Qoder 会话文件。

## 明确不改什么

- 不改变历史会话搜索的结果、入口、索引格式及跳转功能；只替换底层文件读取方式。
- 不修改灵动岛 UI、智能体状态、终端、设置和媒体功能。
- 不删除或关闭 token 统计。
- 不修改 token 计算口径、去重规则和本地历史数据。
- 不修改 MCP 工具、MCP 配置或智能体控制灵动岛的能力。
- 不进行无关重构，不更换 Electron，不调整产品功能开关。

MCP 多进程问题留到第二阶段独立设计和验证，避免两个高风险变量混在一个改动中。

## 方案选择

### 采用：逐行读取 + 启动串行回填

- `parseCodexTokens` 和 `parseClaudeTokens` 使用文件流逐行解析，不再使用 `readFile + split`。
- Codex 仍取最后一条累计 token 数据和最后一次模型设置。
- Claude 仍累计 assistant usage，并按 request ID 去重。
- 损坏或尚未写完的 JSON 行继续跳过，不阻断统计。
- 启动回填一次只解析一份文件；一份完成后再处理下一份。
- 单个文件失败只记录日志，不影响其余文件和应用启动。

用户可见行为保持一致。唯一可能变化是：存在多份历史文件时，token 看板完成全部启动回填的时间会晚几秒，但首份结果可以正常产生，应用其他功能不等待回填。

### 暂不采用：从文件尾部逆向查找

逆向查找对 Codex 很省内存，但 Claude 需要累计整段会话并去重，必须再维护另一套读取逻辑。第一阶段采用统一逐行读取，代码更小、风险更低；如果性能仍不达标，再单独为 Codex 增加尾部索引。

### 不采用：关闭 token 统计或历史回填

这种方式能快速降低内存，但会直接损失产品功能，不符合本次目标。

### 补充验证：历史会话搜索流式索引

第一版预览验证发现，token 解析器单独处理 200 MB 文件已从约 796 MiB RSS 降至约 125 MiB，但整包启动峰值仍约 1.5 GB。将历史会话搜索服务单独运行并重建索引时，复现约 1.82 GiB RSS / 2.06 GiB footprint，确认它是另一条独立根因。

因此，同一分支增加一个独立、可单独回滚的提交：把搜索索引的 `readFile + split` 改成逐行状态机。解析规则、20,000 字符上限、文件游标、索引结构和搜索结果保持不变。不会通过关闭搜索功能来换取性能。

## 数据流

1. 应用启动后，现有 watcher 列出最近的 Codex 会话文件。
2. 回填队列取出一个文件。
3. 解析器逐行读取并更新少量累计状态，不保存全文和全部行。
4. 解析结果继续进入现有差分、去重和 StatsService 逻辑。
5. 当前文件完成或失败后，队列再处理下一份。

事件完成时触发的单会话采集仍走同一解析器，行为不变。

## 测试策略

严格执行测试先行：先增加会失败的测试，再修改生产代码。

### 功能回归

- Codex 仍取最后一条累计 token 数据。
- Claude 仍累计全部有效 assistant usage。
- 重复 request ID 不重复计数。
- 空文件、缺失文件、损坏行和未写完的最后一行安全返回。
- cache read/cache creation 与 model 结果保持不变。
- 启动回填最大并发数为 1，单文件失败不阻断后续文件。
- 搜索索引不调用整文件 `readFile`，同一 fixture 的搜索结果与旧实现一致。

### 性能回归

- 构造大 JSONL 文件，在受限 Node heap 子进程中解析；旧实现应因整文件复制失败或越过内存上限，新实现应成功。
- 用本机约 150 MB 的真实结构文件做隔离 A/B，只记录大小和内存，不保存或提交会话内容。
- 打包预览版后重复启动采样，分别记录 main、desktop core、MCP 和总量。

## 验收标准

- 所有 token 功能测试和项目现有检查通过。
- 200 MB 会话文件解析结果与旧实现一致。
- 解析 200 MB 文件时，隔离进程峰值显著低于旧实现的约 503 MiB，目标不超过 150 MiB。
- 打包预览版处理同批文件时，WorkIsland main 启动峰值目标不超过 450 MB。
- 单独重建历史搜索索引时，峰值 RSS 目标不超过 300 MiB。
- 无 token 重复入账、漏账或统计口径变化。
- 历史会话搜索、灵动岛 UI 和 MCP 功能不发生代码变更。

## 发布与回滚

- 所有修改只存在于 `codex/perf-memory-slimming` 分支。
- 解析器与启动并发分别形成可审查的小提交。
- 先安装本地预览版验证，不直接替换正式 Release。
- 任一统计结果不一致或功能测试失败时不合并；可按提交独立回滚。

## 第二阶段候选

第一阶段通过后，再单独调查 MCP：区分 Codex 客户端生命周期与 WorkIsland 进程成本，评估轻量转发、共享后台服务和空闲退出。第二阶段必须另有设计、测试和用户验收，不与本分支第一批修复捆绑。
