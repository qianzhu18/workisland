# Token 采集并发风暴与长期内存修复设计

日期：2026-09-22  
分支：`codex/fix-token-collector-memory-storm`

## 问题与证据

瘦身预览版连续运行约 37 小时后，macOS `phys_footprint` 显示应用进程组合计约 1.29 GB；其中主进程约 891–914 MB，历史峰值 3.998 GB。日志确认同一份 93 MB Codex transcript 在一秒内触发 61 次完成事件和 85 次 token 采集。现有 3 秒去重只在采集结束后写入时间戳，因此无法阻止并发任务同时进入。当前 transcript watcher 的增量路径还会一次性分配新增长度的 Buffer，再转字符串并 `split` 全部行。

## 目标

- 同一 `tool + sessionId` 在任意时刻最多执行一个 token 文件扫描。
- 并发重复请求复用正在执行的 Promise，不改变 token 统计结果和调用方接口。
- transcript 增量读取使用固定大小分块和跨块残行，内存不再随单次新增字节数线性放大。
- 保留历史搜索、token 统计、MCP、终端、通知、会话状态及现有工具能力。
- 使用 macOS `phys_footprint` 而不是仅用 RSS 验收。

## 方案选择

采用“按会话单飞 + watcher 分块读取”。

- 不采用仅加时间节流：长文件扫描可能超过节流窗口，仍会并发。
- 不采用全局串行队列：不同会话会互相阻塞，降低统计及时性。
- 不改变事件状态机：重复 lifecycle 事件仍按现有规则处理，只阻止其重复触发昂贵的同一文件扫描。

## 设计

### 1. Token 采集单飞

新增一个小型、独立的 keyed single-flight 调度器。`collectAndReportTokens` 以 `${tool}:${sessionId}` 为键提交实际采集任务：

- 键不存在时执行任务并缓存 Promise；
- 键已存在时直接返回同一个 Promise；
- 成功或失败后都在 `finally` 中删除键，避免永久阻塞；
- 不缓存采集结果，不改变下一次正常完成事件的统计刷新；
- 不把不同 session 或不同工具合并。

这会把本次 85 个并发扫描压缩为 1 个，同时保留原有累计值、基线差分和三秒上报去重逻辑。

### 2. Transcript watcher 分块读取

`readIncrement` 不再按 `stat.size - lastReadSize` 一次分配内存。改为固定大小块循环读取，并在 tracked file 上保留未结束的 UTF-8/JSONL 残行：

- 每块只处理完整行；最后一段残行留到下次增量；
- 文件截断时同时重置 offset 和残行；
- 每条完整 JSONL 仍调用现有 `processLine`，事件顺序与字段保持一致；
- 单次新增再大，临时字符串和 Buffer 都被固定上限约束。

### 3. 可观测性

重复采集被合并时记录 debug 日志，包含脱敏后的工具和 session id，不记录 transcript 内容。测试通过调度器状态验证并发上限，不新增用户设置。

## 测试与验收

先写失败测试，再写实现：

1. 100 个相同 key 的并发请求只能执行一次底层任务，并得到同一结果。
2. 不同 key 可以独立执行；失败后 key 会释放并允许重试。
3. watcher 读取跨块 JSONL、跨块 UTF-8 字符、尾部半行、文件截断，产出与原实现一致的事件序列。
4. 以大尺寸临时 transcript 验证每次读取请求不超过固定块大小。
5. 运行相关测试、全量测试和 macOS 打包。
6. 对真实打包版制造重复完成事件压力，记录主进程与进程组 `phys_footprint` 的启动值、峰值和回落值；不得再出现同会话几十个并发采集。

## 风险边界

本修复不承诺 Electron 达到原生应用的基础内存，但必须消除已确认的数 GB 并发峰值。若结果一致性、真实打包功能或物理足迹任一不达标，不合并主分支。
